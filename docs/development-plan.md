## A. Project Understanding

Song Shout is a social web application where friends communicate by sending each other
songs instead of (or alongside) text. The primary interaction is the **Shout** — a song
reference sent from one user to another.

The central flow is:

**Choose friend → Choose song → Send shout**

Key product rules:

- The app is **not** a music streaming/hosting/downloading service. Songs are external
  references stored as metadata + provider links.
- Preview playback (when the provider returns a `previewUrl`) is rendered in a standard
  `<audio>` element pointing directly at the provider-hosted URL. No re-hosting, no proxying.
  If preview is missing or fails, the fallback is an external provider link — this is intended
  behavior, not an error.
- Friendship is mutual and required: users can only send Shouts to friends.
- A recipient can have **one reaction per Shout**.
- A reply is still a Shout (V1). No chat, threads, comments, or groups.
- V1 is a portfolio-quality, secure, full-stack project. It should feel personal, simple,
  music-focused, and fast.

## B. Architecture

Layered architecture with strict separation of concerns:

```text
UI (React components / Server Components)
        ↓
Application layer (Server Actions, Route Handlers, services)
        ↓
Domain/services (friends, shouts, notifications, songs, reactions)
        ↓
Infrastructure
   ├── Supabase client (browser-safe) / admin client (server-only)
   ├── MusicProvider interface → SpotifyProvider (server-only, credentials isolated)
   └── Validation, error handling, utilities
        ↓
External: Supabase (Auth/Postgres/Storage/Realtime) · Spotify API · Vercel
```

Constraints:

- The music provider abstraction must NOT leak Spotify-specific structures into the rest of
  the application. Business logic depends on `MusicProvider` / `SongResult` only.
- Authorization is enforced at the database (RLS) and server boundary. Frontend hiding is
  never treated as authorization.
- Provider credentials and Supabase service-role keys are server-only, never exposed to the
  browser.
- The database is the source of truth; Realtime only delivers change events.

Request/action style:

- **Server Actions** for authenticated mutations (send request, accept, decline, remove friend,
  send shout, react, mark notifications read, update profile, upload avatar).
- **Route Handlers** for provider-backed reads that need server-side credentials and caching
  (song search, song lookup).
- **Server Components** for initial page data; **Client Components** for interactivity
  (search-as-you-type, realtime subscription updates, audio playback).

## C. Database Design

PostgreSQL schema (via Supabase migrations). All tables live in the `public` schema with
snake_case columns, `timestamptz`, UUID primary keys generated by default.

### profiles

| column | type | notes |
| --- | --- | --- |
| id | uuid PK | FK → `auth.users(id)` ON DELETE CASCADE |
| username | text UNIQUE NOT NULL | lower-case, 3–20 chars, `[a-z0-9_.]`, immutable after creation |
| display_name | text NOT NULL | 1–50 chars |
| avatar_url | text NULL | Supabase Storage public URL |
| created_at | timestamptz NOT NULL | default now() |

- `updated_at` maintained by trigger.
- No password storage here. Supabase Auth is the password authority.

### friend_requests

| column | type | notes |
| --- | --- | --- |
| id | uuid PK | |
| sender_id | uuid NOT NULL FK → profiles | |
| receiver_id | uuid NOT NULL FK → profiles | |
| status | text NOT NULL | CHECK IN ('pending','accepted','declined') |
| created_at | timestamptz NOT NULL | default now() |

- CHECK: `sender_id <> receiver_id` (no self-request).
- UNIQUE: `(sender_id, receiver_id)`.
- UNIQUE: `(sender_id, receiver_id, status)` blocked from duplicating a pending row via
  partial unique index `UNIQUE (sender_id, receiver_id) WHERE status = 'pending'`.
- A pending request is resolved (updated to accepted/declined or deleted) before a new one can
  be created for the same pair.

### friendships

| column | type | notes |
| --- | --- | --- |
| id | uuid PK | |
| user_id | uuid NOT NULL FK → profiles | |
| friend_id | uuid NOT NULL FK → profiles | |
| created_at | timestamptz NOT NULL | default now() |

- CHECK: `user_id <> friend_id`.
- UNIQUE: `(user_id, friend_id)` — prevents duplicate friendships in either direction.
- Single row per friendship pair (always stored with the lower id as `user_id`), enforced
  in the insert path; alternatively a generated `pair_id` unique index. Decision: store
  canonical `(user_id, friend_id)` where `user_id < friend_id` for a fully normalized,
  uniquely-constrained edge. This avoids `(A,B)` and `(B,A)` duplicates.

### song_references

| column | type | notes |
| --- | --- | --- |
| id | uuid PK | |
| provider | text NOT NULL | e.g. 'spotify' |
| provider_song_id | text NOT NULL | |
| title | text NOT NULL | |
| artist | text NOT NULL | |
| album | text NULL | |
| artwork_url | text NULL | |
| preview_url | text NULL | direct provider-hosted audio, may be null |
| external_url | text NOT NULL | |
| duration | integer NULL | seconds |
| created_at | timestamptz NOT NULL | |

- UNIQUE: `(provider, provider_song_id)` — same external song resolves to one reference row.

### shouts

| column | type | notes |
| --- | --- | --- |
| id | uuid PK | |
| sender_id | uuid NOT NULL FK → profiles | |
| receiver_id | uuid NOT NULL FK → profiles | |
| song_reference_id | uuid NOT NULL FK → song_references | |
| message | text NULL | CHECK: length ≤ 280 |
| sent_at | timestamptz NOT NULL | default now() |
| seen_at | timestamptz NULL | |

- CHECK: `sender_id <> receiver_id`.
- A reply is a new `shouts` row; an optional nullable `reply_to_shout_id` FK to self is added
  so replies can be traced to the original Shout (V1 reply feature). (nullable self-FK)

### reactions

| column | name | notes |
| --- | --- | --- |
| id | uuid PK | |
| shout_id | uuid NOT NULL FK → shouts ON DELETE CASCADE | |
| user_id | uuid NOT NULL FK → profiles | |
| reaction_type | text NOT NULL | CHECK IN (small allowlist, e.g. emoji set) |
| created_at | timestamptz NOT NULL | |

- UNIQUE: `(shout_id, user_id)` — one reaction per user per Shout, enforced by DB.

### notifications

| column | type | notes |
| --- | --- | --- |
| id | uuid PK | |
| user_id | uuid NOT NULL FK → profiles ON DELETE CASCADE | recipient of the notification |
| type | text NOT NULL | e.g. 'friend_request', 'shout_received', 'reaction' |
| actor_id | uuid NULL FK → profiles | who triggered it |
| related_entity_id | uuid NULL | shout / friend_request id |
| read_at | timestamptz NULL | null = unread |
| created_at | timestamptz NOT NULL | |

- Index on `(user_id, read_at DESC)` for the list + unread badge.
- Index on `(user_id, created_at DESC)`.

Indexes summary: friendship unique, friend_request unique, song_reference unique, reaction
unique, notifications user/read, shouts `(receiver_id, sent_at DESC)`.

Database protection of invariants: self-friend/self-shout/self-request CHECKs, uniqueness for
friendships/requests/reactions/song refs, cascades for owned rows, RLS on every table.

## D. Authentication & Authorization

### Authentication (Supabase Auth)

- Email/password auth via Supabase Auth (default `auth.users`). No custom password storage.
- Next.js client (`@supabase/ssr`) with cookie-based session for App Router (middleware +
  `createServerClient`). Server Actions use the server client; client components use the
  browser client.
- Profile row created automatically on first sign-up via a DB trigger on
  `auth.users` → `public.profiles` (created with display name = email prefix until the user
  sets one; username required at onboarding). This keeps identity ↔ profile clean.
- Middleware protects `/dashboard`, `/friends`, `/shouts/*`, `/notifications`, `/profile`,
  `/send`. Auth pages redirect signed-in users to the dashboard.

### Authorization (RLS + server)

RLS enabled on all tables. Helper functions:

- `auth.uid()` for current user id.
- `public.is_friend(a uuid, b uuid)` → true if a canonical friendship row exists.
- `public.are_friends()` convenience using `auth.uid()`.

Policies (SELECT/INSERT/UPDATE/DELETE as listed):

- **profiles**: SELECT — all authenticated users (needed for friend search by username);
  UPDATE — only own row (`auth.uid() = id`); INSERT — own row (via trigger, generally
  service-side); DELETE — none (auth delete is out of V1).
- **friend_requests**:
  - SELECT — participant (`sender_id = auth.uid() OR receiver_id = auth.uid()`).
  - INSERT — `sender_id = auth.uid()` **and** receiver exists and is not self and no existing
    active friendship and no existing pending request (checked in policy with subqueries,
    plus a server-side re-check for clear errors).
  - UPDATE — only `receiver_id = auth.uid()` AND status transition pending→accepted/declined.
  - DELETE — `sender_id = auth.uid()` (withdraw own request).
- **friendships**: SELECT — participant; INSERT — participants only (server enforces the
  canonical `user_id < friend_id` ordering + mutual acceptance); DELETE — participant
  (server also reverses the reverse-request state if needed).
- **song_references**: SELECT — any authenticated user (they are non-sensitive metadata
  referenced by shouts the user can see); INSERT — only via server flow (service role or
  server action using admin client); no client-side INSERT policy.
- **shouts**: SELECT — sender or receiver; INSERT — `sender_id = auth.uid()` AND receiver is a
  friend (policy calls `are_friends()`); UPDATE — receiver only, limited to `seen_at`
  (and sender none); DELETE — none.
- **reactions**: SELECT — participant of the shout (sender or receiver); INSERT —
  `user_id = auth.uid()` AND user is the receiver of the shout AND shout exists; UPDATE —
  `user_id = auth.uid()` (change reaction); DELETE — `user_id = auth.uid()`.
- **notifications**: SELECT — `user_id = auth.uid()`; INSERT — none client-side (created by
  server action via service role); UPDATE — `user_id = auth.uid()` limited to `read_at`;
  DELETE — none.

Server-side (Server Action) validation re-checks every authorization decision — RLS is the
backstop, not the only gate. Song search route handler is authenticated.

## E. Music Provider Architecture

```text
src/lib/music/types.ts        → MusicProvider, SongResult interfaces
src/lib/music/registry.ts     → provider registry by id
src/lib/music/spotify/…       → SpotifyProvider + normalized mapper + error handling
```

- `SongResult` and `MusicProvider` match the specification exactly. `previewUrl` is the direct
  provider-hosted audio URL or `null`.
- `SpotifyProvider` uses the Client Credentials flow (app-level token, server-side), caches
  tokens, and normalizes Spotify search/track responses into `SongResult[]`. Never expose the
  Spotify client secret or token to the browser.
- Errors are classified: user errors (validation), provider errors (unavailable, rate limit,
  invalid response, null preview), infrastructure errors. Provider errors surface as clean
  user messages; technical details are logged server-side.
- Song search endpoint (`/api/songs/search?q=`) runs on the server, validates the query, calls
  the provider, and returns normalized results. Cache-aware (simple in-memory TTL or
  `unstable_cache`) to respect Spotify rate limits.
- New providers (Apple Music, YouTube Music) implement the same interface and register by id;
  the rest of the app is unchanged.

## F. Vercel + Supabase Initialization Guide

### 1. Next.js + Git

```bash
npx create-next-app@latest song-shout --typescript --tailwind --eslint \
  --app --src-dir --import-alias "@/*" --use-npm
cd song-shout
git init            # if not already a repo
git add -A && git commit -m "chore: initialize nextjs application"
```

### 2. Supabase

- Create a project at `https://supabase.com` (Song Shout). Note Project URL + anon key
  (public) and service_role key (server-only).
- `npm i @supabase/supabase-js @supabase/ssr`.
- Enable Supabase CLI for local dev: `npx supabase init`, `npx supabase link --project-ref <ref>`.

### 3. Database migrations

- Create migration SQL files in `supabase/migrations/`:
  1. `0001_profiles.sql` — profiles table + trigger on auth.users + updated_at trigger.
  2. `0002_social.sql` — friend_requests, friendships (+ helpers `is_friend`).
  3. `0003_songs.sql` — song_references.
  4. `0004_shouts.sql` — shouts (+ reply_to_shout_id).
  5. `0005_reactions.sql` — reactions.
  6. `0006_notifications.sql` — notifications.
  7. `0007_rls.sql` — enable RLS on all tables + policies.
- Apply: `npx supabase db push` (or `db reset` in local dev). Never hand-edit production.

### 4. Supabase Auth

- Providers: Email enabled. Redirect URLs configured for localhost + Vercel preview/prod.
- Sign-up flow wired to `@supabase/ssr`. Profile trigger creates the profile row.

### 5. Supabase Storage

- One private-ish/public bucket `avatars`. Public bucket (public URLs for avatars) with
  strict path policy:

```sql
-- policy: user can write only under their own folder
storage.objects policies:
  INSERT  → bucket_id='avatars' AND (storage.foldername(name))[1] = auth.uid()::text
  UPDATE  → same
  SELECT  → bucket_id='avatars' (public read)
```

- Client uploads directly to the bucket (using anon key) into `{userId}/{uuid}.{ext}`.
- File type allowlist: jpg/png/webp. Size limit enforced client + server (≤ 5 MB).
- On new upload, delete old avatar object; profile `avatar_url` updated to new public URL.

### 6. Supabase Realtime

- Enable Realtime for `public.notifications` (replica identity full) — the client subscribes
  filtered by `user_id=eq.<auth.uid()>` to update the unread badge + list live. DB remains the
  source of truth; on refresh, notifications load from the database.

### 7. Spotify credentials

- Spotify Developer Dashboard → create app → record Client ID (public-ish, still server-only
  in practice) + Client Secret (server-only).

### 8. Environment variables (see also `.env.example`)

| variable | visibility |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | public |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public |
| `SUPABASE_SERVICE_ROLE_KEY` | server-only, secret |
| `SPOTIFY_CLIENT_ID` | server-only |
| `SPOTIFY_CLIENT_SECRET` | server-only, secret |
| `NEXT_PUBLIC_APP_URL` | public (base URL) |

### 9. Vercel

- Import repo → project settings → add all env vars for Production, Preview, Development.
- Deploy. `vercel` dev/preview uses the same env file. Enable production envs only for prod
  values; never commit real secrets.

## I. Risks

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Spotify preview URLs expire / blocked / region-limited | High | graceful `onError` fallback to external link; treat as intended behavior |
| Spotify API rate limits | Medium | token caching, result caching, debounced search |
| Spotify access token not available (missing credentials) | Medium | clear server-side error message, feature-gated search |
| RLS misconfiguration exposes data | Medium | policies reviewed per table per operation; service role confined to server |
| Service-role key leaked to client | Low | never in client components; env naming + lint guard |
| Duplicate friendship/request races | Medium | unique constraints + canonical ordering + transactions |
| Realtime flooding / over-broad subscriptions | Medium | narrow filters, unread badge only, DB remains source of truth |
| Missing provider fields (album/artwork null) | Medium | nullable columns + UI fallbacks |
| Avatar path traversal / overwrite | Low | storage path policy bound to uid + UUID filenames |
| Scope creep (chat, playlists, AI…) | Medium | enforce V1 exclusion list; defer with explicit request only |
